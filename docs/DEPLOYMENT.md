# Deployment and operations

The standard product path is an authenticated HTTPS app with an online Worker,
D1, remote AI, and hosted execution. A phone user needs only the authorized web
session, not a PC, Node.js, Ollama, or a model download. This guide separates the
private Sites beta from independent hosting and the optional legacy runtime.

Native authenticated MCP read/proposal and negative HTTPS guards are verified.

is pushed and [remote CI 38336981415](https://github.com/tatu-project/tatu/actions/runs/38336981415)
passed Windows and Linux. Positive web cookie login/CRUD/mobile visuals, real AI

## Private Sites beta: first deployment lane

The canonical project is `apps/cloud`, with managed project metadata in
`apps/cloud/.openai/hosting.json`. It declares the `DB` D1 binding and MCP
capability. The compiled Worker and two schema migrations are generated by the
repository build; generated exports are not independent product sources.

Maintainers prepare and review the candidate from the repository root:

```sh
npm ci
npm run ci
npm run export:site
```

The export is under ignored `tmp/cloudsite`. The reviewed source was published
through the authorized Sites workflow with owner-only access; future releases
repeat review before publication. Do not turn the private app into an
unauthenticated public API. Configure runtime values/secrets through the hosting
platform, not committed files:

| Name                      | Purpose                                                                  |
| ------------------------- | ------------------------------------------------------------------------ |
| `AUTH_MODE=sites`         | Managed identity adapter                                                 |
| `SITE_PROJECT_ID`         | This deployment's managed project identity                               |
| `SITES_OWNER_PRIVATE=1`   | Required owner-private managed boundary                                  |
| `SITE_ORIGIN`             | Exact deployed HTTPS origin                                              |
| `DB`                      | Managed D1 binding with both migrations applied                          |
| `TATU_ENCRYPTION_KEY`     | Runtime-only base64-encoded 32-byte operational envelope key             |
| `TATU_ENCRYPTION_KEY_ID`  | Envelope key version, such as `v1`; preserve existing decryptability     |
| `AI`                      | Optional available Workers AI binding; do not assume Sites provides it   |
| `SCHEDULER_ENABLED=false` | Keep disabled until the native dispatch bridge is connected and verified |

Optional sponsored Groq requires an authorized runtime `TATU_GROQ_API_KEY` and
explicit `TATU_ENABLE_SPONSORED_GROQ=true`. It is not automatically enabled or a
way to evade provider limits. End-user Groq BYOK uses the HTTPS connection form
and durable encrypted owner-scoped storage. Its external allowance is unknown.
Do not paste keys into chat, URLs, docs, Git, or logs.

The current Site has no `AI` binding or Groq credential, so live general chat is
unavailable until the owner connects an authorized key through the HTTPS form.
The `v1` operational encryption secret is configured natively; its raw value
must never enter repository files or documentation. Current/previous-keyring
rotation is bounded and fixture-tested; a real owner credential was not used.

The Worker has a `scheduled` handler, but publishing code alone does not create a
managed scheduling bridge. Keep the Site scheduler unavailable until its actual
native automation invokes the bounded dispatcher and a real due occurrence is
observed. Manual **Testar agora** is separate evidence.

A real owner-private platform-boundary dispatcher probe succeeded against the
empty queue without creating user data, tasks, schedules, keys or LLM calls.
Later native MCP preparation created only a transient QA proposal, not a task.
The Site flag remains false; readiness is not unattended task proof.

In Sites mode with the owner-private flag, `/api/system/run-due` accepts allowed
same-origin requests behind the private gateway; it does not distinguish owner
browser sessions from platform service access. Probes show token-auth access
succeeds and anonymous access fails, not service-only exclusivity or ordinary
owner rejection. This is a single-owner QA limitation: require independently
verifiable dispatcher authority before wider sharing or multiple owners.
Native automations are empty, and prompt-based `create_schedule` has no verified
mapping to the code dispatcher. No schedule, entitlement or exact free Cron
cadence is guaranteed. Portable code Cron remains a separate hosting account,
deployment and allowance requirement.

## Independent Workers/D1/Access: second deployment lane

This configuration is portable and independent of the founder's Site/account.
It has not yet been verified live. It requires your own eligible Cloudflare
account, D1 allowance, controlled HTTPS hostname, Access identity/application
policy, and an available authorized remote AI route. Check provider pricing and
limits before provisioning; no unlimited-free or account-eligibility guarantee
is made.

From the repository root, install/build/check as above, then:

```sh
cd apps/cloud
npx --no-install wrangler login
npx --no-install wrangler d1 create tatu --config wrangler.jsonc
```

Use the installed pinned Wrangler; the command may ask you to authorize your own
Cloudflare account. Configure `wrangler.jsonc` for your deployment:

1. Replace `database_id` with the D1 database created in your account. Keep the
   binding `DB` and `migrations_dir` pointing at the two repository SQL files.
2. Add your controlled hostname as a Worker route/custom domain; `workers_dev`
   remains disabled. Protect that hostname with an Access allow policy for the
   intended owners before sharing it.
3. Set `AUTH_MODE=cloudflare-access`, `SITE_ORIGIN` to the exact HTTPS origin,
   `ACCESS_TEAM_DOMAIN` to your team hostname, and `ACCESS_AUDIENCE` to that
   application's AUD tag. The API verifies the identity token, not a supplied
   user/owner ID.
4. Enable `SCHEDULER_ENABLED=true` only for the reviewed portable Cron deployment.
   Its trigger is once per minute; task-local timezone determines the due task.
   Do not infer live scheduled success from configuration alone.
5. Keep the `AI` binding only if Workers AI is available in your account. If it
   is absent, use optional authorized Groq BYOK or retain an honest unavailable
   AI state. Do not replace it with local Ollama or an automatic paid route.

From `apps/cloud`, apply migrations, set the operational key through Wrangler's
secret prompt, and deploy:

```sh
npx --no-install wrangler d1 migrations apply tatu --remote --config wrangler.jsonc
npx --no-install wrangler secret put TATU_ENCRYPTION_KEY --config wrangler.jsonc
npx --no-install wrangler deploy --config wrangler.jsonc
```

The equivalent root scripts are `npm run migrate:portable --workspace @tatu/cloud`
and `npm run deploy:portable --workspace @tatu/cloud`. Secret operations
can create/deploy a Worker version; review the account and target before doing
so. `SYSTEM_RUN_TOKEN` is a runtime secret only if an independently authenticated
system dispatcher is explicitly configured, not a browser/owner credential.
[D1 setup](https://developers.cloudflare.com/d1/get-started/),
[migrations](https://developers.cloudflare.com/d1/reference/migrations/),
[Worker secrets](https://developers.cloudflare.com/workers/configuration/secrets/),
[Access token validation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/).

Deployment/identity migration maps verified issuer/subject to internal owners.
Reauthenticate and perform an explicit reviewed remap; copying raw Site user IDs
or changing the envelope key/key ID silently can break isolation or decryptability.
See [security architecture](SECURITY-ARCHITECTURE.md).

## Verify and operate

Before calling either lane a verified beta, record the deployed revision/URL,
owner sign-in, unauthenticated/cross-owner denial, D1 persistence, mobile layout,
connection state, real MCP installation/calls, and actual scheduled delivery or
an explicit scheduling gap. Live inference needs an available authorized binding
or key; label fixtures and unavailable routes. Follow
[the release checks](RELIABILITY-TRIAL.md); no 30-day waiting gate remains.

Current bounded behavior:

- AI news only, through curated public feeds: 1–10 cited stories. Facts are RSS
  excerpts, not claimed AI-written facts; in-app results retain source links.
- Suggested founder task: daily 09:00 in `America/Sao_Paulo`, targeting NotebookLM
  Audio Overviews. Tatu exports cited text for manual NotebookLM import, where
  the user generates audio. Automatic Tatu audio API integration and native
  account/device actions remain separate work; text alone does not complete
  the audio goal.
- Per-owner AI caps: 8/minute; sponsored 30/day or BYOK 100/day; 4,096 context
  bytes; up to 1,024 output tokens; 2 concurrent requests. Shared budgets and
  external provider limits may be lower. API caps: 240 reads/60 mutations per
  minute per owner.
- Keep the latest 500 terminal executions per owner; pending/running jobs remain.
  Manage cloud backups/retention under your hosting account without publishing
  private database contents.
- Server-decryptable operational encryption is not E2EE. Assistant records are
  plaintext at the application layer, and selected context goes to the provider.
  A client-held password vault is future work, not the connection form.

## Optional legacy Node/SQLite self-hosting

This is a separate local/development path, not the online mobile backend:

```sh
npm ci
npm run ci
npm run dev
```

Open `http://127.0.0.1:3000`. Local storage/outbox default to `data/tatu.sqlite`
and `data/deliveries`; `.env.example` documents installation configuration.
Keep the native API on loopback and never expose its unauthenticated port as the
cloud service. Stop local processes before copying private backups. No model
installation is required for the corrected online product path.

The optional Node profile is legacy developer/API behavior with local SQLite.
Its local-individual `/api/me` projection is not a remote account/session or
logout system; navigating to `/` is local navigation. Shared UI settings still
contain cloud-oriented wording, so this profile is not claimed as a fully
accepted local PWA or online D1 deployment. No separate visual check passed.

Docker is optional. The September 16, 2026 record verified the previous local
image build/startup. October 3 verified the updated Compose configuration and
loopback mapping only; no Docker engine is available on this workstation for a
fresh image/startup check. Preserve `127.0.0.1:3000:3000`; reverify the container
runtime on a Docker-enabled machine before advertising it as current proof.

## Account-dependent handoffs

- **Private owner access:** open the verified published link and complete its
  native Sign in/Entrar flow with the Site owner's account; positive login and
  authenticated CRUD still need verification.
- **Groq inference:** create your own eligible API key at the official provider,
  then submit it only in the app's HTTPS Groq connection form. Revoke it at the
  provider if necessary; removing it from Tatu is not provider revocation.
- **Browser/MCP verification:** enable the platform browser for owner cookie
  login/CRUD/mobile visual QA. Native platform-authenticated read/proposal already
  works; standalone OAuth and broader confirmation/mutations have separate
  acceptance. Refresh/Connect is no longer a blocker for the verified native calls.
- **Independent hosting:** authorize Wrangler/Access in your own hosting account
  and supply deployment bindings/secrets privately. The founder's managed
  identity and private account credentials are not portable.
